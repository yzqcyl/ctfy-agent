# 求解器集群（多 LLM / 多方向并行）可行性评估

> 日期：2026-10-27｜口径：**纯离线分析，未新增任何真机 run、未改任何代码（含并行会话的未提交改动）**。
> 所有数字来自既有实测报告 `runs/bench-web-report.md`、AI 线 `docs/ai-plan.md`、平台源码 `.tools/ctfy-src/` 与本地源码。
> 结论按"能否做 / 值不值得做 / 怎么最小验证"三段给，置信度逐条标注。

---

## 0. 结论摘要

| 问题 | 结论 | 置信度 |
|---|---|---|
| **Q1：提交镜像里能"不同 LLM 走不同方向"吗？** | **不能。** 容器里所有角色被强制成平台下发的单一 `LLM_MODEL`；自备多厂商 key 属违规。 | 高（源码逐行） |
| **Q2：那"同模型、不同策略方向并行"工程上能做吗？** | **能，但要动编排层**（约 400–600 行 + 并发安全），不是配置项。 | 高（架构已核） |
| **Q3：做了会涨分吗？** | **现有证据中性偏负，收益未被测量**：换模型不涨分且路径重叠 80%；失败主因（预算/环境）会被 ×N 放大。 | 中（数据有限） |
| **Q4：现在值不值得做？** | **不值得先做全量集群。** 应先把"单路在墙钟内把预算用满"（≈600k）测掉；集群实验放在那之后，且成本上限 ≥5M token。 | 中高 |

一句话：**"不同 LLM"这条路在生产契约里根本不存在；"不同方向并行"在数学上等于拿深度换广度，而我们现在连"深度"都没测满。**

## 1. 先拆题：设想里其实混了三件不同的事

| 代号 | 形态 | 生产可行性 | 已有证据 |
|---|---|---|---|
| **C1** | 不同 LLM（Kimi / DeepSeek-Pro / GLM…）各跑一路 | ❌ **契约禁止** | A/B 已证伪（0/3 vs 0/3，慢 2.27×，覆盖更窄） |
| **C2** | **同一个模型**，N 路锁定不同策略族（侦察/注入/越权/读取面…） | ⚠️ 工程可行，收益未测 | 无直接实验；唯一边界证据是"失败=策略塌缩" |
| **C3** | 单路串行"换族"干预（工作区未提交的 `STRATEGY_SIMILARITY_LIMIT`） | ✅ 已写、未真机测 | 0 次真机；设计上吃 1× 成本的多样性 |

> 关键判断：用户设想里"不同 LLM 走不同方向"在**提交物里会退化成"同模型走不同方向"**（见 §2.1）。所以真正要评估的是 C2，而 C1 只剩"本地练习场调参"的价值。

## 2. 硬约束（全部有源码/文档坐标，可逐条复核）

### 2.1 单模型、单密钥（决定性）

- `src/ctfy_agent/agent_main.py:213-218`：`_build_config` 把每个角色的 `model` 键 **pop 掉**，统一到 `config.max_tokens`。
- `src/ctfy_agent/agent_main.py:473-483`：`llm_factory` 收 `model` 参数但不使用，**永远用 `config.model = LLM_MODEL`**。
- `docs/b1-adapter-plan.md:113-117`：网关会**用注册模型改写请求里的 model**，所以"多角色多模型名毫无意义"。
- `runs/site/standards/CTFY-0001.md:130-150`：容器只拿到一份 `LLM_API_KEY` / `LLM_MODEL`；`LLM_API_KEY` 可能为空且**必须大声失败**（禁止回退自有 key）。
- `docs/submit-image-runbook.md` §3：提交时要选定"由哪个 provider 付费"——即费用由注册的那一个 provider 承担。

→ **结论**：C1 在生产不存在。本地能跑多模型（.env 里 Paratera 网关有多个模型名），但那只是练习场行为，不能进提交物。

### 2.2 单实例配额 1

- 赛事硬约束 `max_instances_per_team_effective=1`（HANDOFF §5）。
- 推论：并行只能发生在**同一道题、同一个实例内部**，不能靠"多题并行"或"多实例并行"增加吞吐。

### 2.3 容器资源（够用，不是瓶颈）

- `.tools/ctfy-src/ctfy/core/constants.py:270-272`：`HARNESS_MEMORY_MIB=8192`、`HARNESS_CPUS=2`、`HARNESS_PIDS=512`。
- N 路线程是 I/O 等待（LLM + HTTP），2 核够；Python stdlib `threading` 可用。

### 2.4 墙钟：**未知，但很可能是集群的死穴**

- `.tools/ctfy-src/ctfy/eval/external.py:98`：外部 harness 默认 `_DEFAULT_TIMEOUT_S = 1800`（30 分钟），可由部署侧改。
- `docs/b1-adapter-plan.md:324`：`eval_timeout_s` 实际值在部署侧配置，**无法从源码校准**；官方标准 CTFY-0001 全文没有单次运行时长条款（只有 `max_turns`）。
- `docs/b1-adapter-plan.md:98-101`：超时后平台仍会读 `result.json`（所以 provisional rollup 有效，但**跑不完的 token 全白烧**）。
- `runs/site/standards/CTFY-0001.md:358`：task.json 里 `max_turns` 示例是 **40**；`null` 才是无预算。若正赛给 40，按实测 ~9.5–10.5k token/调用，**token 天花板约 400k，800k 预算根本用不满**。

### 2.5 费用自负

- 每个 token 由注册的 provider 计费（runbook §3）。集群 = token 成本 ×N。

## 3. 核心算术：集群是"深度换广度"，总预算不会变多

实测吞吐（`runs/bench-web-report.md` §4.2）：**99,313 token / 290.4 s ≈ 342 token/s**。

若单次评测墙钟为 `T`，则**单题可消耗 token 上限 ≈ 342 × T**：

| 假设墙钟 T | 单题 token 上限 | 800k 单路要多久 | 2 路各分到 | 3 路各分到 |
|---|---|---|---|---|
| 20 min (1200 s) | **~410k** | 39 min（超） | 205k | 137k |
| 30 min (1800 s，外部 harness 默认) | **~615k** | 39 min（超） | 308k | 205k |
| 60 min (3600 s) | **~1.23M** | 39 min（可行） | 615k | 410k |

关键推论：

1. **墙钟若 ≤30 min，800k 单路本身就跑不完**（800,000/342≈2,340 s≈39 min）。"预算放回 800k"必须同时确认 `max_turns` 与墙钟，否则预算是纸面数字。
2. **并行不增加总 token**：N 路共享同一实例、同一墙钟，总量仍是 `342×T`，只是切成 N 份 → **每路更浅**。
3. 所以集群的净收益条件是：
   `P(至少一路在其 T/N 预算内解出) > P(单路在 T 预算内解出)`。
   目前**没有任何实测支持左边**；唯一相关数据（A/B 路径重叠 80%）偏向否定。
4. 现存失败题的平均消耗（medium 158,986、≈150k 上限被掐断）说明：**单路连 150k 都没用满就被预算掐了**——先给单路更多预算，是把水加到杯子里的最直接方式。

## 4. 收益证据盘点（全部来自既有实测，未重推）

| 事实 | 数值 | 对集群的含义 |
|---|---|---|
| 归档/解出 | 16 道 / 5 道 = **31.2%**（easy 5/9、medium 0/4、hard 0/3） | 基数低，任何 ×N 都要先付 N 倍钱 |
| 失败题 attempts | **11 道全为 0** | 失败在"没产出候选 flag"，不在"提交错" → 需要的是**新路径**，不是更多次提交 |
| 失败主因 | 预算耗尽 6、协调者空转 2、实例起不来 2、自认完成 1 | 只有"预算耗尽"部分可被 ×N 预算缓解；实例失败会被 ×N 放大 |
| A/B 换模型 | 0/3 vs 0/3，慢 **2.27×** | **换模型不是多样性来源** |
| 路径重叠（SAMPLE-007） | K2.7 38 条 vs Pro 10 条，8 条包含；Pro 独有 **2** 条（干净 Jaccard≈0.20） | 两路独立假设不成立；实际互补 ≈2/38 |
| 2 路理论/现实 | 独立假设 `1-(1-0.312)²=52.7%`；报告 §12.4 现实估计 **38–46%（低置信）** | 上限不清，下限接近 31% |

**为什么"策略塌缩"不能直接当成集群的正面证据**：策略塌缩发生在**同一路内部**（同一 POST 重发 5 次被账本拦）。串行换族干预（C3）就能以 1× 成本打断它；并行只是把"可能换方向"变成"同时换方向"，代价是预算除法。

## 5. 工程可行性（能做，但要动结构）

现状（逐条核对）：

- `src/ctfy_agent/crew.py:435-480`：`Crew.solve` 是**单线程顺序编排**（协调者一轮 → delegate 一个专家 → 等它跑完）。
- `src/ctfy_agent/crew.py:479` + `:369-386`：**同一个 `Solver` 对象跨所有 delegate 复用**，专家只换 LLM。`Solver` 持有 `_http_cache`（`solver.py:210`）和 cookie jar（`solver.py:943`）→ 现在所有角色共享一份会话/缓存。集群必须改成**每路一个 Solver**，否则 cookie 互相污染。
- 共享状态无锁：`Budget` 是纯计数器（`budget.py`，无 `threading`）；`Ledger` 无锁（`ledger.py`）；`Store.append_transcript` 直接 `open("a")`（`state.py:372-374`）；`Store.save` 有文件锁（`state.py:300/320`）。
- MCP 客户端每次调用 `self._opener.open`（`mcp_client.py:115/141`），共享一个 opener；并发调用建议在平台层加串行锁（平台调用本身很便宜）。
- `verify_answer` 是**无副作用 oracle 探测**、不写提交记录（`.tools/ctfy-src/ctfy/mcp/server.py:742-759`）→ 天然可做 N 路候选的裁定通道。
- 只有 coordinator 有 `submit` 权（`config/agent.json` coordinator.platform 含 `submit`；专家无）→ 需要一个"收集候选 → 校验 → 单点提交"的汇总器。

改动清单与工作量（估算）：

| # | 改动 | 规模 |
|---|---|---|
| 1 | `ClusterRunner`：起实例一次、N 路线程、每路独立 Solver/Budget/Ledger 视图 | ~150 行 |
| 2 | 并发安全：Budget/Ledger/transcript 加锁，平台调用串行化 | ~80 行 |
| 3 | 汇总器：候选去重 → `verify_answer` → 首个正确即 `submit`；全灭时交回 T/N 报告 | ~80 行 |
| 4 | 失败隔离：实例失败/LLM 429 时全路硬停（与 P0 修复共用） | ~60 行 |
| 5 | 配置与开关（路数、每路策略族、预算切分） | ~40 行 |
| 6 | 离线用例（假 LLM/假平台：N 路并发、预算互不越界、提交唯一、异常不击穿） | ~150 行 |

→ **约 400–600 行 + 用例；2–4 个工作日**；还要**重建 v3 镜像 + 重新送审**（当前 v2 已冻结，不能改）。

风险：

- 回归风险真实存在：M5.5 那次压缩改动曾让 `report` 证据校验连挂，**连续 3 个 run 各烧 ~260k**才解出（`docs/ai-plan.md` §7.4）。集群是比压缩更大的结构性改动。
- 掉进"状态化靶子互相踩"的坑（见下节）。

## 6. 容易被忽略的硬风险：N 路共享实例 = 共享服务端状态

实例配额 1 → N 路打的是**同一个靶子进程**，共享的不只是 HTTP 连接，还有：

- **会话/登录态**：很多靶子注册即登录、再登录会踢掉旧会话（038/039 实测踩过）。两路各自注册 = 互相踢下线。
- **一次性/轮转凭据**：flag/token 按会话或时间轮转时，A 路取到的值可能在 B 路动作后失效。
- **共享业务状态**：工单号、账本、管理员摘要这类单例数据（039/044 形态），并发写会互相污染证据。
- **限流/风控**：目标侧按 team/IP 限速时，N 路 = 自己的 N 倍流量，更容易被 429/封。

→ 即使做了集群，也建议 **"只读侦察并行 + 写操作串行"**，或每路独立会话并用 `verify_answer` 复验。这会把理论收益再打一折。**这一条没有实测，属设计推断，置信度中。**

## 7. 若要验证：最小实验设计（成本可控、能回答问题）

**先决条件**：先补 §2.4 的三个未知（0 token 或极低成本）：
1. 正赛 `eval_timeout_s` 实际值（问主办方/看文档/一次长跑观察）；
2. 生产 `max_turns`（决定 800k 是否能花出去）；
3. LLM 网关并发上限（2–3 个并发小请求即可探，token 成本可忽略）。

**实验（等单路 600k 结果出来后再做）**：

| 组 | 配置 | 题 | 单题总预算 | 预估 token |
|---|---|---|---|---|
| 对照 A | 单路、不换族 | 3 道 medium：SAMPLE-009、AGENTBENCH-002、AGENTBENCH-005 | 600k | ≤1.8M |
| 实验 B | 2 路、锁定 2 个策略族（侦察 vs 会话/越权） | 同上 3 道 | 2×300k | ≤1.8M |
| 实验 C（可选） | 2 路、同模型但两份相同提示 | 同上 1 道 | 2×300k | ≤0.6M |

指标：解出率、**唯一路径数 / Jaccard**、候选 flag 产出率、墙钟、实例失败次数、`attempts>0` 的题数。
判据：若 B 相对 A 的解出率提升 <1 道，且 Jaccard >0.6，则**枪毙集群路线**（3 道题样本小，但足以否定"显著收益"）。

**为什么对照要用"600k 单路"而不是"150k 单路"**：因为 150k 已被证明是掐断点，拿它当对照会高估集群。只有"同样墙钟、同样总 token 预算"下的对比才有意义——这正是 §3 的算术。

## 8. 建议（go / no-go）

1. **C1（不同 LLM 集群）：no-go。** 生产契约不允许；练习场已被 A/B 证伪。不要再为它花开发时间。
2. **C2（同模型多方向并行）：现在不做全量工程。** 先做 §7 的对照实验；且它必须排在"单路预算拉满"之后——如果单路 600k 就能把 medium 解出，集群边际收益进一步缩水。
3. **C3（串行换族干预）：1× 成本，最该先测。** 它已经在工作区（B1）里，但按你的决定我没动；测它需要跑真机（260k 级预算）。
4. **若最终要做 v3，顺序应是**：实例失败硬停 → 单路在墙钟内把预算用满（≈600k）→ 换族干预实测 → 最后才评估集群。
5. 提交线不受影响：v2 已冻结，以上全部是"是否值得做 v3"的问题。
