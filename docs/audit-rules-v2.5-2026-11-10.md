## 1. P0-1：没有出题能力（最大缺口）

### 规则原文

- §一：「智能体赛道另设**出题环节**，审核通过的题目同时作为人机协同赛道正式赛的赛题。」
- §二(一) 第 66-68 行：「平台测试及入围赛设置若干道模拟题，对智能体赛道团队的**解题/出题 Agent** 进行初步测试」
- §二(二) 第 76 行：「每队的出题 Agent 在轮次内**最多提交一道**符合主题的 Web、Pwn、AI Security 题目」
- §二(四) 第 97 行：「【出题分】与【解题分】按赛事规定加权计算（**各占 50%**），形成智能体赛道最终排行榜。」
- §五(二)：「智能体出题、解题须**自主**完成……正式任务期间不得人工注入赛题分析、提示、代码、指令或答案。」

### 我们的现状

`src/ctfy_agent/agent_main.py:553-562`：

```python
# 3) 只支持 instance / qa 模式（defence/engagement/awd 显式拒绝，不烧钱）
run_mode = str(task.get("run_mode") or "")
if run_mode not in ("instance", "qa"):
    _write_rollup(..., stop_reason="refused", writeup=f"unsupported run_mode={run_mode!r}")
    return 0
```

`grep -rn "authoring" src/ctfy_agent/*.py` → **0 命中**。`docs/authoring-plan.md` 里已把「窗口段 agent 编排」标为 **P1 未做**。

### 为什么是 P0

1. 最终排行榜 = 出题分 50% + 解题分 50%。出题分为 0，意味着**解题必须做到满分档才有一半的机会**。
2. 更早的雷：11/14 入围测试明文说要测「解题/出题 Agent」。如果入围赛就下发出题类任务，我们现在会写 `refused` 并退出——不是少得分，是**直接判为不支持**。
3. 平台冻结镜像后才允许跑，11/21 当天不能临时补。所以这件事必须在 **11/14 之前**进入镜像。

### 建议

- 先查清平台怎么下发「出题」任务：CTFY-0001 的 5 种 `run_mode`（instance/qa/defence/awd/engagement）里**没有 authoring**，说明出题不是靠 run_mode 区分，而更可能是：① 出题比赛下发的 `competition_id` / `deliverable` 不同；② 出题走 MCP 的独立工具族（`docs/authoring-plan.md` 说 23 个出题工具）。**这一步必须实测**，不能猜。
- 短期可做的事（不依赖上面的结论）：把 `run_mode` 白名单改成「未知模式不 `refused`，而是落到通用解题链路」，并把 `deliverable` 字符串喂进协调者提示——至少不会因为一个字不认识就整题弃权。

## 2. P0-2：正式赛 1B token 上限，我们只有单题刹车

### 规则原文

第 111-113 行：「正式赛阶段仅可访问主办方提供的智谱大模型（https://open.bigmodel.cn/\*），并具有 **Token 总量限制 1B**。」
第 107 行：「不得通过代理、重定向、子进程或其他方式**绕过网络和资源限制**。」

### 我们的现状

- `config/agent.json`：`max_tokens_per_challenge = 800000`、`max_llm_calls = 240` → **单题**级。
- `src/ctfy_agent/budget.py` 的 `total_tokens` 是单个 `Budget` 实例内计数，生命周期 = 一道题。
- 没有任何跨题/跨进程累加器，也没有「剩余额度」概念。

### 风险评估

单题 800k × 30 题 ≈ 24M，离 1B 很远，**平时不会撞**。但两个场景会：
1. 平台重跑/重试同一题（我们支持「跨进程继承，重跑接着算」，只对同一题有效）。
2. 若正式赛题量远超预期，或单题预算被调高到 2M+。

按 1B / 800k = **1250 题·次** 的余量看，正常题量撞不上。所以这条的实质风险不是「超限」，而是**平台侧额度耗尽后我们没有任何降级手段**（不会自动缩预算，只会一道道题全部 `halted`）。

### 建议

1. 加一个读 `$CTFY_WORK_DIR/../quota.json`（或环境变量）的全局累加器——**前提是平台真提供了额度查询接口**，需要先确认；不要凭空造。
2. 无条件可做的：把 `max_tokens_per_challenge` 从 800k 降到 400k 左右，靠「步数少而准」而不是「堆预算」（现有 12 步 / 240 calls 的实际消耗中位数远低于 800k）。
3. 正式赛前把 `.env` 换成智谱的 `LLM_BASE_URL` / `LLM_MODEL`，**别改代码**——`agent_main.py:241-243` 已经优先读平台注入的 `LLM_*`，代码侧无需改动。

> ✅ 同一条规则里有一处我们**做对了**：第 105 行「解题 Agent 无公网访问权限，只能访问授权的平台接口、大模型网关及题目入口」。我们 `agent_main.py:241-243` 优先读 `LLM_API_KEY` / `LLM_BASE_URL` / `LLM_MODEL`（平台注入的网关），只在缺失时回落到 `config/agent.json` 的百炼地址。这条是通的，不用改。

## 3. P1-3：晋级口径（30 支）与首关日期（11/14）

### 规则原文

- 第 64-68 行：「智能体赛道**最多入围 150 支队伍**……排名进入前 150 名有资格进入初选赛」——150 是**入围上限**，不是晋级线。
- 第 70-72 行：「按经核验的智能体赛道入围赛解题成绩，选出**前 30 支队伍**进入正式赛。有效队伍不足 30 支时按实际数量晋级。」
- §二(一) 人机协同才是「前 100 名」晋级正式赛（第 23 行）——**两条赛道的数字不同，容易串**。
- 第 13 行：「11 月 14 日开放模拟测试作为比赛调试与**入围测试日**。」

### 我们的现状

- `PROGRESS.md:62`：「报名 2026-10-15 起；**入围测试 11-14~15，初选赛 11-15 10:00–20:00**；正式 11-21~22。agent 赛道上限 150 队。」
  - 「11-14~15」把两天写成连续区间，实际 11/14 = 入围测试日、11/15 = 初选赛，是**两个不同性质的日子**。
  - 「10:00–20:00」手册里**没有**，是我们的假设，不应写成事实。
  - 缺「前 30 进正式赛」这个关键数字。

### 影响

- 今天 11/10，**距 11/14 只有 4 天**，v7 还没提平台审核。11/14 当天就要真跑 agent 打分，这是第一次真实检验。
- 前 30 才进正式赛 → 出题分（50%）只有进正式赛才拿得到。**进不了前 30，出题能力白做；但为了进前 30，又必须先有出题能力（入围测试可能考）**——这两件事互为前置，所以 P0-1 不能等 11/21。

## 4. P1-4：切智谱时 `enable_thinking` 会外发

### 我们的现状

`src/ctfy_agent/llm.py:146-147`：

```python
if os.environ.get("LLM_ENABLE_THINKING", "").strip().lower() in ("0", "false", "no", "off"):
    payload["enable_thinking"] = False
```

百炼认这个字段（关思考模式，避免 `max_tokens` 全烧在 `reasoning_content` 上）。**智谱 GLM 不认**——它用 `thinking: {type: "enabled"/"disabled"}`（或根本不接受该字段）。多传未知字段的行为视网关实现而定：宽容的忽略，严格的直接 400。若是 400，`llm.py` 的重试逻辑会把它当不可重试错误抛出 → **整题报废**。

### 建议

两选一，改动都很小：
1. 按 base_url 分流：只有 host 含 `dashscope` 时才加 `enable_thinking`；
2. 正式赛的 `.env` 里直接不设 `LLM_ENABLE_THINKING`（当前逻辑「不设置 = 完全保留端点默认」，等于零改动）。

> 推荐 2（零代码风险）+ 1（兜底）都做。

## 5. P1-5：双赛道报名冲突（需人工确认，代码无关）

### 规则原文

- §二(二) 第 33 行：「团队及任意队员**不得重复参加**智能体团队赛道、人机协同赛道，同时入围两个赛道的队伍/队员**仅能选择其中之一参赛**。」
- §五(一)：「每人仅可注册**一个**个人账号并加入**一支**参赛队伍……禁止共享、出借、代登录或冒用身份。」

### 需要确认的三件事

1. 团队是否**只**报了智能体赛道？有没有队员另报了人机协同？
2. 平台侧账号是否**唯一**（我们记录里是 `d0ef391d` 一个账号下挂了 8 个 harness——多 harness 是镜像版本，不是多账号，属正常）。
3. 有没有用过别人的 token 做本地联调（`CTFY_TOKEN` 是谁的）？「Agent 使用平台分配的专用凭据」，用别人的 token 跑平台算冒用。

## 6. P2-6：运行记录封存边界

### 规则原文

第 89 行：「正式赛结束后，需先**封存 Agent 运行记录**及参赛材料，再按统一安排公开题解、受理投诉工单并核验成绩。」

### 我们的现状

`runs/` 写在 `/ctfy/work/runs/<challenge>/`（`agent_main.py` 里 `config.runs_dir = work_dir/"runs"`），transcript 完整记录了每轮工具调用与响应。**但容器结束后平台是否保留 `/ctfy/work`，我们不知道**（CTFY-0001 只说 `result.json` 会被读走，`stdout` 不被读取）。

### 建议

低风险，但值得在 11/14 前提一个工单/问一句官方：正式赛的运行记录是平台自己归档，还是需要镜像侧写进某个固定路径。若是后者，我们现在就该把 transcript 落到那个路径。

## 7. P2-7：自校验 300 次/题 的合规边界

### 规则原文

第 243 行：「禁止……**爆破 Flag 提交接口**和篡改日志。」

### 我们的现状

- `submit_answer` 有 `submit_limit=3`（严格）。
- `verify_answer` 走的是平台的「判题但不写提交记录」工具（`platform.py:20` 注释：可白试），`oracle_limit=300`。

严格讲 `verify_answer` 不是提交接口，300 次不违「爆破提交接口」的字面。但如果 agent 退化成「穷举候选值 → 逐个 verify」，从行为上很像爆破，被投诉时不好解释。

### 建议

`oracle_limit` 从 300 降到 80~100，并在提示里明写「verify 只用于验证**有推理依据**的候选，不得穷举」。成本几乎为零，风险直接消掉。
