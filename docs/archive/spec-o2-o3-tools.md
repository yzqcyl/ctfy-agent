## 2. O2'：burst 分组前先归一化（唯一要做的）

### 2.1 缺口（实测）

- 可解析的 `values` 型 burst 115 次：原始分组 **245 → 归一化后 191**（压缩仅 22%），但个别题碎片化严重：
  CTFARENA-017 一次 burst：13 组 → 归一化后 4 组；CTFARENA-015：4 组 → 1 组。
- 根因：响应体回显了 payload（`{}`/`{v}` 出现在错误页/回显字段），每个 payload 一个组 → 同一个"结果类型"被拆成十几组，
  模型要自己从垃圾组里找规律，且注入 token 白花。

### 2.2 设计

在分组前对正文做**归一化后再分组**（仅用于分组键，输出仍展示该组代表样本的原始 head）：

1. 把本次 burst 的每个 `values[i]` 在正文中出现处替换为 `<V>`；
2. 再剥常见时变/非确定性片段（与 `progress.stable_text` 同源思路）：
   ISO 时间戳、epoch 秒/毫秒、UUID、≥16 位 hex、`\d{6,}` 长数字；
3. 归一化后的正文按 `BURST_READ_BYTES` 截断作为分组键；
4. 合并后组对象增字段 `"raw_count": <合并前组数>`，`"i"` 列表合并去重、升序；
5. 输出排序不变（按 count 降序），长尾折叠逻辑沿用。

**兼容性**：无 `values` 的竞态模式（race）不存在回显问题，走原路径；有 `values` 时输出结构只增一个可选字段，
旧字段语义不变（`count`/`status`/`head`/`i`）。

### 2.3 验收（并入 `tests/smoke_http_cache.py` 或新增 `tests/smoke_burst_group.py`）

1. 24 个 values、响应正文回显 payload → 归一化后组数 < 原始组数，且 `raw_count` 正确；
2. `i` 合并后不重复、升序；
3. 无 values 的 race 模式输出与旧实现逐字节一致（快照）；
4. 归一化不误合：状态码不同/正文差异 > 截断长度 的组仍分开；
5. 合法 JSON 结构不被破坏（`json.loads` 可解析）。

### 2.4 预期收益（诚实：小）

- 输出 token：单次 burst 输出通常 <1k tok，压缩 20% ≈ 100–200 tok/次；16 题约 **5–10k tok**——**不是主要杠杆**；
- 真正的价值是**信号质量**：13 组碎成 4 组后，"24 个 payload 只有 4 种响应"一眼可见，减少模型误读与后续重复探测；
- 因此排期在 O1a（多 pattern grep，≈4% 预算）之后，属"顺手做"。
