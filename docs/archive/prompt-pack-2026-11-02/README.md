## 二、**在动手之前还需要确认的 6 件事**（这是本次的关键缺口）

这份包能让人"改得动"，但**还不能让人"改得对"**。缺的是下面这些——都已经标好了，需要决策：

### 1. v5 镜像到底建不建？（阻塞 T1/T2）

提示词的改法是"告诉模型 v5 起有 capstone"。如果 v5 最终不建，这句就是**换了个姿势接着骗模型**——
和现在"写着 v4 有、实际没有"是同一类错误，只是晚一期发作。

`Dockerfile` 已经改好（capstone 5.0.3 + sha256 钉死 + 构建期反汇编自检），但**本机 Docker 引擎起不来，
从未真建过一次**。所以需要一句明确答复：v5 建，还是不建？

- 建 → 按 `09` 的 T1 写"v5 起内置"；
- 不建 → 提示词里必须写"**本环境没有 capstone，别去 pip install**"，且不能提"v5"。

### 2. 评测池太小，改完无法 A/B（影响"怎么算改好了"）

11-03 实测：rev 池 3 道（解出 2）、pwn 池 4 道但 3 道需 VPN 不可达，只有 1 道离线可跑。
**这个样本量不足以区分"提示词改好了"和"运气好"。**

要么先把池子扩到 ≥8 道 rev / ≥5 道 pwn（需要能连的实例或离线二进制），要么明确接受
**这次只做结构验收**（`08` 的 7 条硬检查），不宣称效果提升。二选一，别模糊。

### 3. 范围问题：只改提示词，还是允许动工具？（影响 T3 的天花板）

证据很硬：63 次 rev 会话里 `shell` 619 次、`elfpeek` 106 次，只有 38% 的会话用过它。
模型不是没看见提示词，是**权衡后不干**——因为工具一次只能看一个视图，5 个视图 = 5 步，
而写个脚本 1 步跑完。

**只改提示词，最多做到"明确分工、减少内耗"，做不到"让模型爱用工具"。**
要真正解决，得给 `elfpeek` 加一个 `view=all`（一次返回 info+sections+symbols+strings 的摘要），
或者让它支持 `offset` 区间批量输出。这是**代码改动**，不在本次范围内，但必须知道天花板在哪。

### 4. 目标模型是否固定？

现在 rev / pwn 都绑 `DeepSeek-V4.1-Flash-1017`，`temperature=0.2`，`max_tokens=8192`。
提示词是给这个模型调的。**换模型必须重调**，现在这份包对它有效、对别的不一定。

如果比赛当天可能换模型，就要额外要求"提示词不能依赖特定模型的服从性"（例如不能只靠一句
"不要这样做"来约束行为，得给可执行的替代动作）。

### 5. 验收口径怎么定？

现在能测的只有"解出/未解出"。但这次改动主要影响的是**步数效率**和**token 效率**
（比如把 5 次 elfpeek 合并成 1 次脚本，省 4 步）。如果只看 solve rate，改动可能完全看不出效果。

建议同时看三个数：`solve rate`、`平均步数`、`平均 token/题`。哪一个优先，需要定。

### 6. pwn 的失败数据从哪来？

rev 有 63 次会话可分析，pwn 只有 12 次且 9 次死在 VPN 上。**pwn 现在的改动只能靠推理，不能靠证据。**
要拿到证据，需要一批能跑的离线 pwn 二进制（不需要真实例，栈溢出/格式化串的静态部分就够）。
