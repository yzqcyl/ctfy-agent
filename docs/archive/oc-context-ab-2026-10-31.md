# O-C 上下文降本 A/B：结论是「这两个旋钮无效」（2026-10-31）

**一句话：把上下文滑窗 32k→18k、工具输出硬上限 6000→3500，对平均 prompt 没有任何影响
（14358 → 14345 tokens），解题率不变（3/10 vs 3/10）。不要翻默认值。**

## 1. 实验设计

| 项 | A 臂（现状） | B 臂（候选） |
|---|---|---|
| `max_context_tokens` | 32000 | 18000 |
| 工具输出硬上限 | 6000 字符 | 3500 字符 |
| 其余 | 同模型（paratera `DeepSeek-V4.1-Flash-1017`）、同提示词、同 500k 预算、同 10 题 | ← 同 |

题目集（10 题，含 2 道回归哨兵）：CTFARENA-014（上轮解出）/ 024 / 033 / 047、
CYBENCH-013（上轮解出）/ 018 / 024、AGENTBENCH-002、GAUNTLET-LITE-001、UPLOADLABS-021。

## 2. 结果

| 指标 | A（32k/6000） | B（18k/3500） | 变化 |
|---|---|---|---|
| 解出 | 3/10 | 3/10 | 0 |
| 总 token | 4.7M | 4.6M | −2% |
| 总调用数 | 303 | 292 | −4%（噪声内） |
| **均 prompt tokens** | **14358** | **14345** | **−0%** |
| prompt p90 | 19403 | 19571 | +1% |
| prompt p99 | 25232 | 23784 | −6% |
| prompt 最大值 | 25601 | 24314 | −5% |
| ≥25000 的调用数 | 4 | 0 | −100% |
| 单题最大 prompt 均值 | 20599 | 20240 | −2% |

逐题看，B 臂唯一明显收益是 `CYBENCH-013`：508k/32 调用 → **289k/20 调用**（省 43% token），
其余 9 题基本持平或略差（`CYBENCH-024` 406k→508k）。n=10 太小，不能当规律。

## 3. 为什么无效（关键诊断）

从 transcript 的 `usage.prompt_tokens` 拆解：

| 观测量 | 数值 | 含义 |
|---|---|---|
| 首调用 prompt | **1814** tokens | system + 题面 + 事实板（这是成本「地板」） |
| 相邻调用增量中位 | **+570** tokens | 每步新增工具结果与推理 |
| 增量 > 0 的步骤占比 | **92%** | 上下文几乎每一步都在涨 |
| 单题 prompt 峰值 | ~20.4k | 才刚到 32k 窗的 2/3 |

也就是说：真正的成本是**稳态累积**（avg 14.4k ≈ 地板 1.8k + 22 步 × 570），
而 `_compact_history` 的软压缩**不动当前链段与最近 3 步**（`KEEP_TAIL_GROUPS` + `seg_start`），
所以下调 max_context_tokens 只切到了「极少数越窗的尾部」（p99 25.2k→23.8k），
对均价毫无影响。工具上限 6000→3500 也一样：真正进上下文的渲染长度本来就只有 1600 字符
（`tool_text_chars`），硬上限极少被触发。

## 4. 结论与后续

1. **不采纳** 18k/3500：无收益、多一处偏离、还引入一处 per-problem 方差。
2. 保留本次的**参数化改造**（`AGENT_MAX_CONTEXT_TOKENS` / `AGENT_TOOL_TEXT_MAX` 环境变量可覆盖，
   默认仍 32000/6000）——后续做 A/B 只需换 env，不用改代码。
3. 真要降本，杠杆在「地板与累积速率」，按预期收益排序：
   - **`tool_text_chars` 1600 → 900**（每步少 ~175 tokens，30 步省 ~5k，预期 −20~25%）；
   - **`KEEP_TAIL_GROUPS` 3 → 2** 或让软压缩也动当前链段的旧步（省得多但可能丢工作集，需要防「变笨」）；
   - **事实板/FactsBoard 摘要瘦身**（地板 1.8k 里占比要看下一轮拆解）。
4. 若要验证第 3 条，最小成本是 5 题单臂（≈2.5M token、20 分钟），不必再跑 10 题双盲。
