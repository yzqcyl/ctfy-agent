## S1 致命：单个坏 URL 可杀死整个 run

**#1（✅ 已修复）`normalize_url` 对非法端口抛未捕获的 ValueError，`_ledger_gate`/`_ledger_after` 均在 try 块外裸奔**

- 位置：`ledger.py:76-97`（`urlsplit(...).port` 在端口 >65535 或非数字时抛 `ValueError`）；调用链 `attempt_key → normalize_args → normalize_url`。
- 裸调用点共 4 处：`solver.py:637`、`solver.py:856`（gate，在 `try: self._execute` **之外**）；`solver.py:660`、`solver.py:880`（after，同样在 try 之外）。`_execute` 里那句 `except Exception` 兜底（`solver.py:645`）救不到它——异常在进入 `_execute` 之前就抛了。
- **实测**（探针 3，端到端假 MCP）：模型第一步发 `http_request http://127.0.0.1:99999/` → `solve()` 整体崩溃 `ValueError: Port out of range 0-65535`，而不是按设计回灌 `[执行异常]` 让模型自愈。
- **攻击面/触发面**：① 模型 typo（很常见）；② **提示注入**——题面属不可信来源，嵌入 `http://x:70000/` 之类的 URL 被模型转抄进 `http_request`，一次注入即可终止该题全部剩余尝试（预算白烧、转录戛然而止）。crew 路径同样中招（专家 `run_role` 的 gate 一样裸奔）。
- **修复方向（待批准后实施）**：`_ledger_gate`/`_ledger_after` 内部把 `ledger.seen/record` 包进 try——归一化失败就当「没见过」放行，让 `_execute`→`LocalTools._check_target` 的 `ToolError` 路径兜底（`tools_local.py:237-239` 已能干净拒绝非法端口）；或让 `normalize_url` 自身对 `.port` 做 try。前者更彻底。

## S2 高：A2 回归，delegate 去重完全失效

**#2（✅ 已修复）`normalize_args("delegate")` 仍读 `task` 字段，而 A2 后调用方已改传 `objective` → 同 role 的所有派活撞成同一个键**

- 位置：`ledger.py:132-134` 读 `args.get("task")`；调用方 `crew.py:466`（seen）、`crew.py:481`（record）传的是 `{"role": ..., "objective": ...}`。
- **实测**（探针 1）：不同 objective 被判重复 `True`；两次不同派活后 `ledger.order` 条数 = 1（应为 2）；去重键实际为 `delegate|{"role": "web", "task": ""}`。
- 三重后果：
  1. 首次派活之后的**每一个** delegate 都被贴「与第 N 步相同」假警告 + `duplicates_intercepted` 虚高（探针 4 复现：objective 从「探测 /login」换成「分析响应」仍被判重）；
  2. 协调者的 A2「推进」信号（`len(ledger.order)` 增长，`crew.py:523-526`）永远不增长 → **PlanTrack 把正常换目标误判为停滞**；
  3. 派活历史在账本里折叠成一条，假设聚类与 M2 取证全部失真。
- **46/46 为什么没抓到**：`case_ledger_crew` 只测了「同 objective 判重」「缺 objective 拒绝」「旧格式 task 兼容」，缺「**不同 objective 不得判重**」这条反向断言——测试盲区与缺陷点完全重合。
- **修复方向**：`normalize_args` 的 delegate 分支改成 `{"role": ..., "objective": ...}`（旧格式在 `crew.py:462` 已折进 objective，无需兼容两个键）；同时补反向单测。

## S3 中

**#3（✅ 已修复）`note`/`report` 也被记进账本（`NO_DEDUPE` 只挡 gate 不挡 record）**

- 位置：`ledger.py:33` 的 `NO_DEDUPE` 只在 `_ledger_gate`（`solver.py:178`）生效；`solver.py:660`、`solver.py:880` 的 `_ledger_after` 对**每个**工具无条件 `ledger.record`。
- **实测**：`note`×2 + `report`×1 → `order` 条数 = 3，digest 出现「已试过 note {"text":"线索A"}」。
- 后果：① note 是记忆不是尝试，「已试过（勿重复同一参数）」摘要语义被污染；② **停滞的模型每步写不同内容的 note 就能伪造「推进」信号**——直接破坏 A2「推进只认账本新增的非重复尝试」的确定性承诺；③ report 把专家结论文本当「尝试参数」入库，长报告挤占 `max_tried=400` 与 digest 空间。
- crew 协调者路径不受影响（只显式记 delegate）；单 agent `solve()` 与专家 `run_role` 两条路径都中招。
- **修复方向**：`_ledger_after` 对 `name in NO_DEDUPE` 直接返回（或 `Ledger.record` 开头跳过）。

**#4（✅ 已修复）HTTP 缓存跨题不清理，批量跑可能把 A 题响应体喂给 B 题**

- 位置：`solver.py:159` `self._http_cache` 是 **Solver 实例级**；缓存键 `(netloc, path_q)` **不含 challenge_id**（`tools_local.py:377`）；全库无一处 `.clear()`。`auto.py:53-61` 顺序跑多题、同一个 Solver 实例。
- 风险：平台回收 IP:port 给下一题实例时，B 题对同 host:port 的 GET 直接命中 A 题缓存，返回 `cached: true` 的旧 body——**静默喂错数据**，模型可能追错方向或漏 flag。单独跑一题无影响；**A4 批量基线正好在计划内**，会踩。
- **修复方向**：`solve()` 入口清一次缓存，或缓存键加 challenge_id（前者更简单，跨 delegate 共享语义不受影响——delegate 都在同一题内）。

## S4 冗余

**#5（✅ 已修复）账本摘要在专家初始任务里被注入两次**

- 位置：`crew.py:263-265`（`_delegate` 把 `_prior_digest()`——内含 `ledger.digest()`——附加到任务尾部）+ `solver.py:753-755`（`run_role` 又前置一份 `ledger.digest()`）。
- **实测**（探针 4）：第二轮专家任务 773 字符中账本摘要完整出现 2 次，逐字重复。

- **修复方向**：删 `run_role` 里那段前置（`_prior_digest` 位置更优——它同时携带上一轮专家结论）；注意单 agent `solve()` 路径仍需保留自己的账本注入。

**#6 专家结论三份持久化**：delegate 报告同时进 `reports[]`（内存）、`ledger.record` 的 digest、`store.add_note(text[:800])`（`crew.py:487`）。note 里的截断摘要与 reports 内存副本在协调者上下文里功能重叠，属可接受的审计冗余，量级小，记录在案不单独建议改。
