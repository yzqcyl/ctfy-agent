## 二、新发现（上一轮漏掉的）

### A. 滑窗盲区（严重度取决于一个未验证假设）
`_compact_history` 对 messages 计 16k est，**tools（9.2k est）不占预算**。若模型窗口真是 16k：满窗时 12.6k real 消息 + 7.3k real 工具 ≈ 19.9k > 16k → 网关 400。035 未触发恰恰因为历史小。**「16k 模型窗口」本身是既定假设、从未真机确认**——若窗口实际更大，则只是 est 校准偏差（est 对中文低估约 2 倍，对 JSON/英文高估约 25%）。裁工具顺带缓解；根治 = 窗口预算扣除工具+系统开销，或真机确认窗口尺寸。

### B. 逐调用 usage 未落盘（观测缺口，修法最便宜）
transcript 只记 role/tool/args/result；state.json 只有累计。后果：①所有「每轮构成」只能推算（本报告 #5/#6 的下修正是因此只能给区间）；②转录记录数（63 个 assistant 轮次）与 `calls=50` 对不上，无法核对调用构成。修法：`chat` 回包的 usage 随 transcript 记一行——这正是所审文档 §2.7/§2.8 强调的请求层日志，我们恰好缺。

### C. 行为缺口（顺带记录）
035 从未调用 `verify_answer`（免费 oracle）与 `list_hints`。注意：**这不是删这两个工具的理由**——它们便宜（274/346 est）且提示词要求验证；真实运行没用上是行为失败，恰是要修的方向。

## 四、实施结果（2026-10-25 已落地 #1、#2）

- **#1 裁工具 28→13**：`config/agent.json` 与 `crew.py::DEFAULT_ROLES` 的 web 平台面改为 9 个白名单工具。
  实测（真实 config + docs/mcp-tools.json）：工具 schema **9,205 → 3,624 est（−61%）**，单次省 ~4.4k real，
  全 run（~34 次 web 调用）≈ −150k real ≈ **预算 30%**。删掉的 15 个仍留在 `PLATFORM_SCOPE`（协调者/别的角色可用）。
  web 系统提示词 `[0 取材]` 只点名白名单内工具，删干净无「提示词让调、工具面没有」错配（已 grep 复核）。
- **#2 逐调用 usage 落盘**：三处 chat 回包（协调者 / `run_role` / 单 agent `solve`）的转录记录新增 `"usage"` 字段，
  与既有 `set_tokens`（累计）互补，补齐「每轮构成只能推算」的观测缺口。
- **护栏**：`tests/smoke.py` 新增 `case_web_tool_whitelist`（运行时白名单 == 代码兜底 == 9 项；删掉的 15 个
  既不进 web 也未丢出全局；机制级 `_role_platform_names` 解析恰好 9 项）；`case_crew` 补逐调用 usage 断言。
- **回归**：`compileall` 干净；smoke **52 passed / 0 failed**（51 → 52，真实退出码 0）。
- 未动（另行）：#3 http_request 参数、#4 协调者路由、#5 滑窗校准。

## 五、首次真机解出（CTFARENA-006，2026-10-25）

- 结果：**submitted / flag_accepted**，1 次提交即通过；实例由 release_on_submit 自动停止（平台无残留）。
- 用量：**430,873 / 500,000 token（86%）**，56 / 80 次调用，7 / 8 协调者回合，约 11 分钟。
- 成本构成：web 专家 prompt 396,029（占 92%）、协调者 18,617；单次 prompt 中位 **7,739**（035 为 9,980/call，−22%）。
- 解题路径：`/api/preview?url=` SSRF → `file://` 本地文件读 → shell 跑 Python 批量读 10 个目标路径 → flag。
- 工具分布：http_request 35、shell 19、delegate 6、report 4、get_challenge 1、start_instance 1、submit 1。
- 机制验证：A0 题型送达；A1 拦下 2 次完全重复调用（17 个假设）；A2 plan_changes 5；A3 ssrf/lfi 卡命中；verify_answer 免费试答 1 次；submit 1 次即中。
- **结论修正**：shell 不是纯负担——19 次调用里最关键的一次是跑 Python 批量读文件，省掉 10 次独立 http_request；建议保留（容器内确保真隔离即可）。
- 风险：86% 预算一次烧完，没有第二次机会；006 属「较易的 medium」（13 队解出），更难题目大概率预算先尽。
- 顺带修掉一个 P1：`competition_id` 只写在 `cli.py challenges` 子命令里，`crew` + 新 run 目录会导致 `start_instance` 报 `competition_required`（容器里是全新目录，必踩）。改为按 membership 反查（16 场里唯一命中）+ 写回 meta 缓存；显式配置时行为不变。smoke 增至 **53 passed / 0 failed**。
