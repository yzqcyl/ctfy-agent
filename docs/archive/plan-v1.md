## 2. 接入路线（三条，按顺序使用）

### A. 现成 CLI 先验证（10 分钟，只做连通性）
弹窗给的就是这条，直接抄（PowerShell 里用单引号）：

```powershell
claude mcp add --transport http --scope user ctfy 'https://ctfy.tsinghua.edu.cn/api/v1/mcp/' --header 'Authorization: Bearer <令牌>'
```

作用：确认令牌真的能连、工具名长什么样。它只能算「手工验证」，比赛要的是无人值守，所以不做底座。

### B. 自研 MCP 客户端（**v1 交付**）
`src/ctfy_mcp.py`，Python 3.9+ 纯标准库（不装任何依赖，比赛机也能直接跑）：

- 完整走 `initialize` → `notifications/initialized` → `tools/list` → `tools/call`
- 兼容两种响应体：`application/json` 与 `text/event-stream`（SSE，MCP Streamable HTTP 常见）
- 维护 `Mcp-Session-Id`、`MCP-Protocol-Version` 头
- 令牌只从环境变量 / `.env` / 文件读，**不接受明文写在命令历史里**
- 默认只允许只读工具，`submit_*` / `start_*` 之类必须显式 `--allow-write`
- 只有只读调用才重试；写操作一律不重试（防止重复提交）

### C. REST 兜底
若 MCP 层出兼容问题，可用同令牌直接打站点的 REST 接口。需要开赛后抓一次真实请求确认路径，v1 先不做，只在文档里留位置。

推荐顺序：**A 五分钟验证 → B 做底座 → C 备用**。

## 3. v1 范围与验收标准

### 验收清单（逐条可勾，全部通过才算 v1 完成）

| # | 验收项 | 判定方式 | 备注 |
| --- | --- | --- | --- |
| 1 | 令牌可用 | `doctor` 退出码 0，打印 serverInfo、协商后的协议版本、session id | 出错时分清 401/403（令牌）与连接失败（网络/代理） |
| 2 | 工具清单可见 | `tools` 生成 `docs/mcp-tools.json`，含每个工具的 `inputSchema` | 这份 schema 决定 v2 封装层的字段名 |
| 3 | 只读调用成功 | 题目列表 / 队伍信息 / 排行榜，至少两项返回数据 | 顺带确认分页字段（`cursor` / `nextCursor`） |
| 4 | 实例生命周期可逆 | 开赛后对 1 道题 `start` → 拿到 `host:port` → `stop` | 起停可逆、不影响积分，适合先验证 |
| 5 | 提交链路 | **等开赛第一题或平台测试题再验证** | 不要拿错误 flag 试探：可能计错、影响排名或触发风控 |

> 第 5 条是刻意的：v1 只保证「提交代码路径正确 + 本地 flag 格式校验 + 去重」，不拿真实提交做实验。

### 明确不在 v1
解题 agent、pwntools 集成、LLM 规划器、容器镜像、监控告警、并发调度。

## 4. 架构（v2 全貌，v1 只做接口层）

```
                    ┌─────────────────────── 我们自己的运行环境 ───────────────────────┐
  CTFy 平台          │                                                                  │
 ┌──────────┐  MCP   │  ┌────────────┐   ┌──────────────┐   ┌──────────────┐            │
 │ 题目/实例 │◀──────▶│  │ MCP 客户端  │──▶│ 调度器        │──▶│ 解题 agent    │──▶ 证据日志 │
 │ 提交/榜单 │ Bearer │  │ (本仓库)    │   │ 队列/限速/预算│   │ planner+tools │            │
 └──────────┘        │  └────────────┘   └──────────────┘   └──────┬───────┘            │
                     │                                              │ 本地工具             │
                     │                                    ┌─────────┴──────────┐          │
                     │                                    │ shell / http / pwn │          │
                     │                                    │ 沙箱容器            │          │
                     │                                    └────────────────────┘          │
                     └──────────────────────────────────────────────────────────────────┘
```

**每道题一份状态机**（落盘，进程重启可恢复）：

```
new → parsed → instance_up → probing → candidate_flag → verified → submitted → done
                                   ↘ stalled（超时/超预算，放弃但记录）
```

**四条硬约束（写进代码，不靠自觉）：**

1. **提交幂等**：`sha256(flag)` 去重；同一题同一 flag 只交一次；单题提交上限 3 次。
2. **重试分级**：只读接口可重试（指数退避）；`start/stop/submit` 绝不自动重试，失败先查询真实状态。
3. **上下文预算**：每题独立会话；题面存原文，灌给模型的只有摘要；工具输出截断（建议 4KB）。
4. **证据留存**：每题的 HTTP/命令/模型调用落 `runs/<challenge>/`，用于复盘、申诉和赛后调优。

## 5. 运行环境与工具栈（提前打镜像，别在比赛当天装包）

| 层 | 选择 | 说明 |
| --- | --- | --- |
| 机器 | 1 台 8C16G 云主机（或本机 + 1 台 VPS） | 7 天在线，网络稳定优先；在本机跑也行，但要防休眠断网 |
| 运行时 | Docker 一容器一题，网络策略限制出站 | 防止解题脚本互相污染；也方便限时限内存 |
| Web | `requests`/`httpx`、`curl`、`ffuf`、（按需）Playwright | 先做经典漏洞链：注入、越权、SSRF、文件上传、模板注入 |
| Pwn | `pwntools`、`gdb`/`pwndbg`、`one_gadget`、`seccomp-tools` | 这三样必须提前在镜像里装好并锁版本 |
| AI 安全 | 模型 API 客户端、常见 agent 框架源码（LangChain/LlamaIndex 等） | 题目大概率是 prompt injection、工具调用越权、RAG 投毒类，需要读框架源码 |
| 模型 | 主力模型 + 廉价模型分层 | 侦察/摘要用便宜模型，卡住才升级；设每队总预算与并发上限 |

> 依赖策略：比赛机不临时联网装包（时间与稳定性都不可控）→ 赛前 build 好镜像并 `docker save` 备份。

## 6. 合规与风控（比技术先看）

- **只打平台下发的实例**。任何对第三方真实站点的测试都是法律风险 + 直接违规。
- **令牌等同密码**：不进 git、不进日志、不贴群里；用完到「设置 → API 令牌」吊销。本仓库 `.gitignore` 已排掉 `.env`。
- **限速**：起实例、提交都按最小必要调用；题单一次性拉取后本地缓存，不要轮询。
- **不绕过预期难度**（读数据库、猜 flag、找平台自身漏洞）——这类"捷径"通常明文违规。
- **赛前少制造噪音**：不要用起停实例做压测，避免被风控标记。
- 团队协作：建议只有**一台执行机**持有令牌，其他人只做开发和复盘，避免多机抢同一批实例。

