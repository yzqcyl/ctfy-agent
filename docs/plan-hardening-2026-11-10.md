## 1. 三条铁律（这是"不影响解题率"的具体保证）

1. **只在「已经注定失败」的路径上加分支**——401/402、key 全耗尽、实例连续不可达、预算耗尽、就绪超时。
   正常路径（一次调用就 200）跑过的代码**字节不变**，可用 `git diff` 逐行核对。
2. **每个新行为都有开关，默认 = 当前行为**。除了「纯写标注」（只往 writeup 追加文字，零行为变化）之外，
   没有任何默认开启的新动作。
3. **任何自动动作前先落 transcript**，一行说明「为什么动手、动了什么」。事后能判定是救回来的还是误杀的。

验收标准（可量化，不靠感觉）：同一批 SAMPLE 题，**解出数 ≥ v7**、单题 token 中位数不上升、
正常路径的 transcript 行数不变。达不到就回滚。

## 2. 需求 1：API Key 双备选，耗尽自动切换

### 现状

`agent_main.py:241` 只取一个 key（`LLM_API_KEY` → `OPENAI_API_KEY` → `DEEPSEEK_API_KEY`），
`llm.py:_post` 对 401/402 直接抛 `LLMError`（不可重试）→ 整题 `halted`。
11-15 一天预计烧 30–40M token，**单 key 额度打穿就是全盘归零**，这是本项的真正动机。

### 设计

新建 `src/ctfy_agent/keypool.py`（不碰既有文件）：

```
KeyPool(keys: list[str])
  .current() -> str                     # 当前 key
  .rotate(reason: str) -> bool          # 切下一个；无下一个返回 False
  .usage                            # 跨 key 累加（切换不重置，否则 budget 记账错乱）
  .events: list[{idx, fp8, reason, at}] # 只存指纹不存明文
classify(text, status) -> "dead" | "quota" | "ratelimit" | "transient" | None
```

**判定表（只认这四种，其它一律不动）**

| 信号 | 判定 | 动作 |
|---|---|---|
| HTTP 401 / 403 | key 失效/被吊销 | **立即切**，原请求重试一次（不计入 retries） |
| HTTP 402 | 余额不足 | **立即切** |
| HTTP 429 **且** body 命中 `insufficient_quota` / `quota exceeded` / `arrearage` / `额度` | 额度耗尽 | **立即切** |
| HTTP 429 其它（`rate limit`、`TPM`、`RPM`） | 限速 | **不切**，按 `Retry-After` 退避（现有逻辑） |
| 5xx / URLError / Timeout | 服务端抖动 | **不切**（切了更糟） |
| HTTP 400 且 body 含 `model` / `permission` | 新 key 无该模型权限 | 当 `dead` 处理，继续切 |

**硬门禁（合规，不可绕过）**
> 只要检测到**平台注入**的 `LLM_API_KEY`（同时存在 `LLM_BASE_URL`），KeyPool **只装这一个 key，`rotate()` 恒 False**。
> 正式赛的 1B 额度是按平台下发的 per-run handle 计的，用自备 key 绕过去等于违反「不得绕过资源限制」。这条写成断言，不是注释。

**接入点**：`agent_main.py:673` 的 `llm_factory` 把 `KeyPool` 传给每个 `DeepSeekLLM`；
对象各自独立但共享同一个 pool 引用 → 任一角色切换，全局生效。
日志只打 `key#2(ab12cd34)`，**绝不打明文**。

### 危险

| # | 危险 | 后果 | 处置 |
|---|---|---|---|
| 1.1 | 把 429 限速当额度耗尽，多 key 轮询 | 可能被判「绕限速」，也可能加剧封禁 | 只在 body 明确配额类时切；纯限速走退避 |
| 1.2 | 所有 key 都死 | 整题报废（与现在一样），但**更晚**才失败 → 浪费预算 | 全耗尽立即抛 `LLMError(kind=all_keys_dead)`，写 `llm_error` + writeup 注明，不再重试 |
| 1.3 | 新 key 没开通该模型 | 400，被误当服务端错误反复重试 | 400+`model/permission` 归到 `dead`，继续切；切满一圈仍失败则收口 |
| 1.4 | usage 统计被重置 | `max_tokens_per_challenge` 失效 → 烧穿 | usage 挂在 pool 上，切换不重置 |
| 1.5 | 平台注入场景被误切 | **违规** | §硬门禁，代码里 `assert platform_injected: len(pool)==1` |
| 1.6 | key 明文进日志/transcript | 密钥外泄（文档会被提交） | 只存 `fp8 = sha256(key)[:8]`；`tools/secret_scan.py` 已有兜底 |

## 3. 需求 2：实例卡住自动掐断并备注

### 现状

- 已有 `crew.py:428 ENV_FAIL_LIMIT=3`：连续 3 次**专家结论文本**命中环境故障字样 → `stop_reason=environment_error`。
- 已有 `progress.py EnvFailureTracker`：连续 3 次注入提示、6 次建议收口、占比 30% 追加预算提示。
- 缺口：① 判据是「文本关键字」，`connection refused` 在正常 web 侦察里也会出现 → **误判风险**；
  ② 判定后**不停手也不标注实例状态**，只写一句收口理由。

### 设计：三级阶梯（L1/L2 默认开，L3 默认关）

**判据升级为结构化信号**（复用 `progress.failure_kind()`，不新起计数器）：
同一 `instance_id` + 同一 `host:port` 连续 **3** 次连接类失败（`refused` / `timeout` / `502` / `404 网关`）→ `instance_stalled`。

| 级 | 动作 | 默认 |
|---|---|---|
| L1 | 落 transcript：`[实例卡住] id=… host:port=… 连续 3 次连接失败（最后错误原文）`，并给模型一条「先 `get_instance`/`list_instances` 看状态，别继续换载荷」的提示 | **开** |
| L2 | 若平台有 `renew_instance` → **只在「一次都没连上过」时** renew 一次；否则走已有 `_recover_instance_slot`（start 一次，受 `instance_ops_limit=5` 约束） | **开** |
| L3 | `stop_instance` 释放配额 | **关**（`AGENT_STALL_STOP_INSTANCE=1` 才开） |
| 收口 | `stop_reason=environment_error` + writeup 附「实例 id / 卡住判据 / 最后成功的动作 / 已确认事实」 | 开 |

### 为什么 L3 默认关（最关键的一条）

平台实测 `max_rebuilds_per_challenge = 0`，协议文档里**没有**这个字段的语义说明。
「停了还能不能重建」是未知数——**停了建不回来 = 亲手把一道可能的题判死**。
所以掐断的语义定为「**停手 + 标注**」，不是「杀实例」。释放配额只在确认放弃时由人决定。

### 危险

| # | 危险 | 处置 |
|---|---|---|
| 2.1 | 慢启动被当卡死（3 分钟才起来的靶场） | 先由需求 4 给足就绪时间（180s），**就绪等待期间不计入 stalled 计数** |
| 2.2 | 与 `ENV_FAIL_LIMIT=3` 叠加，两个计数器各算各的 → 提前收口 | **共用同一个 streak**，不新增阈值 |
| 2.3 | `renew_instance` 重置靶场状态（前面拿到的 shell/session 全丢） | 只在「一次都没连上过」时 renew；连上过就只 L1 提示 |
| 2.4 | 停实例不可逆 | L3 默认关（见上） |
| 2.5 | 误判「平台整体 404」为本题实例问题 | 判据要求同一 instance_id；平台级故障由 `connect_deadline` 那条链路负责 |

## 4. 需求 3：未解/预算耗尽打标注，第一轮跑完后按解出可能性重跑

### 先说契约边界（这条决定了能做到几成）

CTFY-0001 §2：**一个容器 = 一道题**，跑完写 `result.json` 退出，下一题由平台调度。
所以「我们主动把全部题跑完、再自己重跑一轮」**在平台托管跑法里做不到**——调度权不在我们手里。
能做的只有三件（合起来覆盖 80% 的实际价值）：

### 设计

**(a) 标注（零风险，纯追加）**
写进 `result.json.writeup` 的**最前面**（协议明确：writeup 超长是**截断**不是拒收，且不参与评分）：

```
[未解归档] reason=cut_off | tokens 720k/800k | calls 198/240 | turns 14
阶段=利用（已拿到 admin session，卡在文件读取）
已确认事实：/etc/passwd 可读；flag 路径候选 /flag、/app/flag.txt（未验证）
下一步建议：从 session 的 file 接口读 /app/flag.txt（上次差一步，未试）
可解性=高（同类题历史 70% 在第 2 轮解出）
```

放在最前面是因为截断只砍尾部。

**(b) 侧车 `retry_hint.json`**（`runs/<cid>/` 下）
字段：`stop_reason / tokens_used / calls_used / last_phase / dead_ends[] / confirmed_facts[] / solvability(0-3) / next_actions[]`。
用途：同题被再次调度时，`agent_main` 读它决定「续跑（沿用 state）还是重开（上次是 environment_error）」。
**不塞进 result.json**：协议说多余字段会被忽略，但没必要赌，侧车更干净。

**(c) 续跑能力已存在**
`state.json` 支持跨进程继承（facts / ledger / tool_counts / 逐题状态）。只要平台重跑时复用同一个
`/ctfy/work`，本题第二轮会接着上次的上下文跑，不用从零开始——这是「按解出可能性重跑」能真正省时间的前提。

**(d) 我们能自主调度的唯一场合：本地批跑**
`hunt.py`（离线批跑器，不接平台）可以按 `solvability` 排序重跑。比赛中用不上，**自测和 11-14 练习时用得上**。

### 危险

| # | 危险 | 处置 |
|---|---|---|
| 3.1 | 把猜测塞进 `answers` 换取"可能蒙对" | **绝对禁止**：协议明确 `answers` 走 **per-question wrong-attempt cap**，蒙错会把题号额度烧掉。归档阶段 `answers` 只放**已验证**的值 |
| 3.2 | writeup 太长被截断，标注丢失 | 标注放**第一段** |
| 3.3 | 平台每次给新 work dir → 侧车和 state 都读不到 | 退化为一轮，不报错；代码里 `try/except` 兜住 |
| 3.4 | 可解性打分错，把好题排后面 | 只在批量场景生效；评分用「是否有单步之差 + 是否 environment_error」两个硬信号，不做玄学预测 |
| 3.5 | 新增 `stop_reason` 值 | **不新增**——平台口径可能校验，只用现有的 `cut_off/max_turns/halted/environment_error/done` |

## 5. 需求 4：慢启动能等，但不卡死

### 现状

`solver.py:968 _wait_instance_ready`：deadline **45s** 固定，每次 8s 超时，无退避。
重 Docker 靶场（Java/Node + 初始化数据）常见 60–120s 才可用 → 现在会提前判「未就绪」继续，
后面每个请求都拒绝 → 触发需求 2 的收口。**这两件事是同一条因果链**。

### 设计

- 上限改为 `AGENT_INSTANCE_READY_TIMEOUT`，**默认仍 45s（= 当前行为）**，比赛 `.env` 设 `180`。
- 探测间隔退避：3 → 5 → 8 → 10 → 10…（旧实现固定 8s 连打，15 次里大半是无效请求）。
- 就绪判据不变（非「网关 404」的任意响应即就绪），只 `GET /`，**无副作用**。
- 超时后**不 abort**：写一行 note「实例 X 在 180s 内未就绪，按未就绪继续」，把决定权留给模型
  （它可能选择继续试、换端口、或换路线）。**我们不当裁判**。
- 与需求 2 联动：**就绪等待期间不计入 stalled 计数**，避免「等得久 → 被判卡死」。

### 危险

| # | 危险 | 处置 |
|---|---|---|
| 4.1 | 10h session 被等待吃掉 | 单题最多 180s（3 分钟）；且只等一次，不重复等 |
| 4.2 | 平台整体挂掉时每题都等满 | 由 `connect_deadline`（握手阶段）先兜住；这里只在「实例已创建」后才等 |
| 4.3 | 探测请求被平台当成攻击 | 只 `GET /`，不扫路径，不开并发 |
| 4.4 | 探测日志刷屏占上下文 | 只保留最后一行结论，中间尝试不写 transcript |
| 4.5 | 靶场要求特定 Host/路径，`/` 永远 404 | 判据是「非网关 404 即就绪」——真实 404 也放行，不会死等 |

## 6. 其他可能发生的危险（本轮审查新增，按优先级）

| # | 危险 | 触发场景 | 后果 | 建议 |
|---|---|---|---|---|
| R1 | **镜像审核未过** | 提交被退 | 没有第二次机会（11-13 报名截止、11-14 就测） | 今晚提审，留 3 天缓冲；被打回就改协议细节再提 |

| R5 | **赛段末尾硬切** | `after_close=stop` + `solve_grace_s=900` | 最后 15 分钟实例消失，链路上的题全废 | 剩余 20 分钟时停止开新长链路（协调者提示词一句话） |
| R6 | **transcript 无限增长** | 10h 单题，工具输出 6000 字符/次 | 磁盘写满 → 写 state 失败 → 整题崩 | 目前无上限；建议加「转录超过 N MB 时只记摘要」 |
| R7 | **并发 run 撞 key 限速** | 配额 3，平台并行派 3 题 | 429 连锁 → 三题一起慢 | KeyPool 轮换要在并发下线程安全（加锁）；429 仍走退避不切 |
| R8 | **提交次数烧错题号** | `answers` 里塞未验证值 | per-question cap 用尽，该题作废 | 需求 3 的 3.1 已覆盖；`submit_limit=3` 保持不变 |
| R9 | **时钟偏差** | 容器与平台时钟不同步 | wall-clock 判断提前/延后收尾 | 只用 `time.monotonic()` 做时长，不用系统时间做绝对判断 |
| R10 | **工具 allowlist 不匹配** | 平台 97 tools，我们放行 26 | 调未放行工具 → 失败 → 误判环境坏 | 保持现状（多余工具调了也失败），但 `EnvFailureTracker` 不应把「工具不存在」算环境故障 |
| R11 | **`solved` 字段写错** | 我们写了自己猜的解出列表 | 平台以自己记录为准，字段被标为不实 | 现状正确（只写平台确认过的），不动 |
| R12 | **11-22 被自己出的题反噬** | 平台把本队出的题也派给我们 | 白烧预算且「出题队不得通过本队题得分」 | 审计 #7 待确认；若平台不标记，需靠题面识别（低成本可做） |

## 8. 一句话

四个需求里，**需求 1 和 4 是真救命**（key 打穿 = 全场归零；慢启动误判 = 白送一道题），
**需求 2 的价值主要在「不再白烧」而不是「救回来」**，**需求 3 有一半卡在平台契约上**（我们没法自己重跑）。
最危险的三个隐患不在你列的清单里：**镜像审核（R1）、正式赛 LLM 回落（R3）、长跑进程泄漏（R4）**。
